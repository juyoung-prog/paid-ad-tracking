# VDL Rule Visualization

Use this skill to keep the rule relationship graph in sync with the files that actually exist, then refresh its Storybook visualization. The canonical source is `.claude/skills/rule-visualization`; do not duplicate its workflow, data structure, or the graph data itself.

The single source of truth for relationship data is `src/data/ruleRelationships.js`, which is generated by `scripts/generate-rules.js` (run via `pnpm generate-rules`) and consumed by `src/stories/overview/RuleRelationships.stories.jsx`. Do not hand-maintain a second copy of this graph.

## Required Reads

- Read `.claude/skills/rule-visualization/SKILL.md` for the full source workflow, the 4-step sync sequence, the node/edge/conditionMatrix data structures, and the core principles.
- Read `src/data/ruleRelationships.js` before editing, to see the current `priorityMeta`, `ruleNodes`, `ruleEdges`, and `conditionMatrix` shape. Note its header: it is auto-generated, so prefer regenerating over hand-editing.
- Read `scripts/generate-rules.js` when you need to know exactly which directories are scanned. Today it scans `.claude/rules/` and `.claude/skills/` only. See the re-pointing section below.
- Reference `src/stories/overview/RuleRelationships.stories.jsx` for how the graph renders (hierarchy, node list, edge list, condition matrix).

If the Claude source folder `.claude/skills/rule-visualization` is missing, stop and tell the user this Codex skill depends on that local source path.

## Codex structure re-pointing (SSOT divergence, read carefully)

The source skill treats the `.claude/` directory tree as the physical SSOT for the rule graph: `.claude/rules/*.md` are the rule nodes, `.claude/skills/<name>/SKILL.md` are the skill nodes, and `.claude/skills/<name>/resources/*.md` are the resource nodes. `scripts/generate-rules.js` walks exactly those two directories.

In Codex the rule graph no longer lives only under `.claude/`. It now spans two trees, and the sync must account for both:

| Scope | Claude side (existing) | Codex side (re-pointed, additional) |
|-------|------------------------|-------------------------------------|
| Rules | `.claude/rules/*.md` | (rules remain Claude-side) |
| Skills | `.claude/skills/<name>/SKILL.md` (+ `resources/*.md`) | `.agents/skills/vdl-<name>/SKILL.md` (Codex skills, incl. their `agents/openai.yaml`, `references/`, `scripts/`) |
| Subagents | `.claude/agents/<name>.md` | `.codex/agents/<name>.toml` (Codex subagents) |

Consequences when you sync:

1. Treat `.agents/skills/` and `.codex/agents/` as first-class scan targets in addition to the `.claude/` tree. A newly added Codex skill (`.agents/skills/vdl-<name>/`) or Codex subagent (`.codex/agents/<name>.toml`) is a real node in the graph and must be reflected in `ruleNodes`, with `activates`/`references`/`resources` edges in `ruleEdges` and any relevant `conditionMatrix` rows.
2. Codex skill nodes should carry their `.agents/skills/vdl-<name>/SKILL.md` path; Codex subagent nodes their `.codex/agents/<name>.toml` path. Keep the same node/edge shape the source defines.
3. `scripts/generate-rules.js` currently only walks `.claude/rules/` and `.claude/skills/`. If the user wants the automated pipeline to also emit Codex nodes, the durable fix is to extend that script's scan roots (adding `.agents/skills/` and `.codex/agents/`) rather than editing `ruleRelationships.js` by hand. Flag this to the user; do not silently divergently hand-edit the generated file for Codex entries while leaving the generator blind to them. Extending the generator keeps `pnpm generate-rules` authoritative.

## Workflow summary

Follow the source SKILL.md's 4-step sequence, applied across both trees:

1. Change the target file (add/modify/delete a rule, a Claude or Codex skill, a skill resource, or a Codex subagent).
2. Sync `src/data/ruleRelationships.js`: update `ruleNodes` (add/remove nodes, fix `priority`), `ruleEdges` (`loads|references|activates|resources`), and `conditionMatrix`. Prefer `pnpm generate-rules` when the generator already covers the changed directory; hand-edit only for surfaces the generator does not yet scan (Codex trees), and prefer extending the generator per the re-pointing note above.
3. Reflect the change in the router doc as the source instructs (CLAUDE.md rule/skill references); include AGENTS.md if the repo uses it as the Codex-side router.
4. Tell the user how to verify (see Output Format).

## Output Format

Respond in the user's language. Report:

```
[Sync complete]
- Changed files: <rules / skills / subagents touched, with tree: .claude vs .agents/.codex>
- ruleRelationships.js: <nodes/edges/conditionMatrix updated, or "regenerated via pnpm generate-rules">
- Generator: <"covered by generate-rules" | "generator does not yet scan Codex trees, extension recommended">
- Verify in Storybook: pnpm storybook -> Overview/Rule Relationships
- Optional build check: pnpm build-storybook
```
